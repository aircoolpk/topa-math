## 1) Executive Summary — สำหรับพี่แอร์

### บรรทัดสรุปสั้นที่สุด

**โมเดล Workers Free + Neon Free ใช้ได้ — แต่ Neon จะพังก่อน Workers เสมอ และจุดพังจะมาถึงที่ราว 350 ผู้ใช้ ไม่ใช่ 10,000**

สิ่งที่หนูเจอจากข้อมูลจริง 3 อย่างที่พี่แอร์ต้องรู้ก่อนตัดสินใจ:

**1. เรายังไม่มีผู้ใช้ที่กลับมาใช้ซ้ำเลย — นี่คือปัญหาที่ใหญ่กว่าปัญหาราคา**

จาก DB จริง: 87 เด็กในระบบ แต่ `days_active = 0` ทั้ง 87 คน, `streak_count = 0` ทั้ง 87 คน, `check_in_events` = 0 แถว, `quiz_sessions` = 26 เซสชันตลอดชีวิตจาก 12 เด็ก และมีเด็กคนเดียวที่ทำได้ 14 เซสชัน (ซึ่งเป็น QA seed) เราไม่มี retention data เลยสักวัน ไม่ใช่ D7 ต่ำ — แต่คือ **ไม่มีตัวเลขให้วัด**

> หนูขอพูดตรง ๆ ค่ะ: ปัญหาหลักไม่ใช่ "Workers Free พอไหม" แต่คือ "ทำไมเด็กไม่กลับมาใช้" การย้าย infrastructure ไม่ได้แก้ retention ได้เลย

**2. MRR ปัจจุบัน = 0 บาท (โดยสภาพความจริง)**

`affiliate_commission_ledger` = 0 แถว, `stripe_subscription_id` = 0 คน, `stripe_customer_id` = 3 คน, `paid_at` = 4 คน แต่ 27 คนได้ `membership_status = plus` ผ่าน `manual_grant` และ 6 คนค้างสถานะ `pending_payment` — แปลว่า **ยังไม่มีรายการชำระเงินจริงสักรายการเดียวผ่าน Stripe** แพ็กเกจปัจจุบันที่ราคา 299/599 บาทยังไม่เคยถูกทดสอบในตลาดจริงเลย

**3. Free tier จะพังที่ ~350 ผู้ใช้ — และราคาที่ถูกที่สุดคือการแก้สถาปัตยกรรม ไม่ใช่การจ่ายเงิน**

| ขีดจำกัด | รองรับผู้ใช้ได้ |
|---|---|
| Neon 100 CU-hrs/เดือน/โปรเจกต์ (โดนก่อน) | **~350 คน** |
| Neon 5 GB egress/เดือน | ~571 คน |

เหตุผล: Neon scale-to-zero ใช้เวลา 5 นาทีก่อนปิด compute ถ้าแอปยิง DB แยกทีละ request ผู้ใช้ 1 คนที่ทำแบบฝึก 8 ครั้ง/เดือนจะกิน **6.67 CU-hrs** ซึ่งคือ Neon Free พังที่ **15 คน** แต่ถ้ายุบทุก request ใน session ให้เป็น 1 DB window เหลือ **0.23 CU-hrs** พังที่ **429 คน** — ต่างกัน **28.6 เท่า**

### 2.2 โมเดลต้นทุนและสูตรที่ใช้

**Workers**
- Free: 100,000 requests/วัน, CPU 10 ms/invocation, Memory 128 MB, Static asset requests **ฟรีและไม่จำกัด**[1][2]
- Paid: $5/เดือน + 10M requests รวม + $0.30/ล้าน (เกิน) + CPU 30M ms รวม + $0.02/ล้าน ms (เกิน)[1]

**Neon**
- Free: 100 CU-hrs/โปรเจกต์/เดือน, 1 GB storage/โปรเจกต์ (20 GB ทั้งบัญชี), 5 GB egress/โปรเจกต์/เดือน, scale-to-zero หลัง 5 นาที (ปิดไม่ได้), autoscaling สูงสุด 2 CU[4][5][6]
- Launch: $0.106/CU-hr, $0.35/GB-month, 500 GB egress รวมแล้วเกิน $0.10/GB, **ไม่มีค่าขั้นต่ำ**[4][6]

> **แก้ข้อมูลเดิม:** โจทย์ระบุ "Neon 0.5GB" — ผิดแล้ว ปัจจุบัน Neon Free คือ **1 GB ต่อโปรเจกต์** (เพิ่มจาก 0.5 GB แล้ว)[4][6] ตัวเลขนี้มีผลกับ breaking point ข้อ 2.4

**R2**
- Free: 10 GB-month storage, 1M Class A ops/เดือน, 10M Class B ops/เดือน, egress ฟรี[1]

**Stripe (Thailand)**
- บัตรในประเทศ: **3.65% + ฿10** ต่อธุรกรรมสำเร็จ
- บัตรต่างประเทศ: 4.75% + ฿10 (+2% currency conversion)
- PromptPay: **1.65%** ต่อธุรกรรมสำเร็จ
- คืนเงิน: +฿10[9]

**Affiliate:** 300 bps = 3% ของยอดชำระ (จาก `affiliate_commission_rate_bps` และ `commission_minor()` ใน `apps/api/app/services/affiliates.py`)

#### สูตรหลักที่ใช้ทั้งเอกสาร

```
ต้นทุนต่อผู้ใช้/เดือน (฿)
  = (Workers_USD + Neon_USD) × 35
    + Stripe_fee + Affiliate_fee
    + เนื้อหา_ที่ตัดเฉลี่ยต่อเดือน

CU-hrs ต่อผู้ใช้/เดือน
  = (จำนวน DB window) × (ชั่วโมงที่ compute ตื่น) × (ขนาด CU)

ชั่วโมงที่ compute ตื่น ต่อ 1 window
  = burst (2 นาที) + scale-to-zero tail (5 นาที) = 7 นาที = 0.1167 ชม.

CU-hrs ต่อ 1 window (ที่ 0.25 CU = 1 GB RAM)
  = 0.1167 × 0.25 = 0.02917 CU-hrs

CU-hrs ต่อ 1 isolated touch (กรณีแย่ที่สุด)
  = (5/60) × 0.25 = 0.02083 CU-hrs

จำนวนผู้ใช้ก่อนชน limit
  = limit ÷ CU-hrs ต่อผู้ใช้/เดือน   (สำหรับ Neon CU-hrs)
  = limit ÷ req ต่อผู้ใช้/วัน         (สำหรับ Workers req)

Net ต่อ subscriber (PromptPay)
  = ราคา − (ราคา × 1.65%) − (ราคา × 3%) − เนื้อหา_ต่อเดือน − ค่า infra

LTV (PromptPay)
  = Net ต่อเดือน ÷ อัตรา churn ต่อเดือน
```

### 2.4 Breaking Point — Free tier พังเมื่อไหร่

#### ข้อ 2.4.1 ตารางรวม (สถาปัตยกรรมแบบ batched, 15% paid)

| # | ขีดจำกัด | ผู้ใช้ที่รองรับ | สถานะ |
|---|---|---:|---|
| 1 | **Neon CU-hrs, 1 โปรเจกต์** | **~350** | ⚠️ **โดนก่อน** |
| 2 | Neon egress 5 GB/เดือน | ~571 | ต้องเฝ้า |
| 3 | Neon CU-hrs, 2 โปรเจกต์ (shard) | ~700 | ทางเลือก |
| 4 | Neon CU-hrs, 4 โปรเจกต์ (shard) | ~1,399 | ทางเลือก |
| 5 | Neon storage 1 GB | ~2,048 | ปลอดภัย (12 MB ปัจจุบัน) |
| 6 | Workers 100,000 req/วัน | ~7,653 | ปลอดภัย |

> Neon ให้ **100 CU-hrs แยกต่างหากในแต่ละโปรเจกต์** และ Free อนุญาต 100 โปรเจกต์[4][6] → การ shard เป็น N โปรเจกต์คูณโควตาด้วย N (ต้องมี shard router เพราะ query ข้ามโปรเจกต์ไม่ได้)

#### ข้อ 2.4.2 ⚠️ ตารางที่สำคัญที่สุด — batching ช่วยได้ 28.6 เท่า

นี่คือข้อค้นพบที่สำคัญที่สุดของงานวิเคราะห์นี้ เพราะ Neon scale-to-zero ปิด compute หลัง 5 นาที[6] = **ทุก request ที่แยกจากกันต้องจ่ายค่า wake window เต็ม 5 นาที**

| รูปแบบการเข้าถึง DB | CU-hrs/คน/เดือน | Neon Free รองรับ |
|---|---:|---:|
| **Isolated: 40 req × 8 sessions = 320 touches** | 6.667 | **15 คน** 💀 |
| **Isolated: 40 req × 20 sessions = 800 touches** | 16.667 | **6 คน** 💀 |
| **Batched: 1 window × 8 sessions** | 0.233 | **429 คน** ✅ |
| **Batched: 1 window × 20 sessions** | 0.583 | **171 คน** ✅ |
| **Batched: 1 window × 30 sessions** | 0.875 | **114 คน** ✅ |

> 40 requests ที่อยู่ใน window เดียวกัน กินเพียง **1.40 เท่า** ของ 1 request เดี่ยว — เพราะ burst 2 นาทีกินแทบเท่า tail 5 นาที

#### ข้อ 2.4.3 ⚠️ Workers KV จะโดนก่อน Neon ถ้าใช้ผิดที่

Workers KV Free = 100,000 key reads/วัน[1] ถ้าเอาบทเรียน/question bank ไปเก็บใน KV แล้วให้ client อ่านทุกครั้ง จะโดนที่ **~340 ผู้ใช้** ก่อน Neon

| ข้อควรระวัง | ถูกต้อง | ผิด |
|---|---|---|
| บทเรียน & question bank | เก็บใน **R2** (static assets → Workers requests ฟรีไม่จำกัด[1]) หรือ bundle ใน static assets | เก็บใน KV แล้วอ่านทุก request |
| Skill metadata / quest templates | KV อ่านได้ (เฉพาะตอน login) | KV อ่านทุกข้อ |
| Profile, XP, progress, billing | Postgres | — |
| Analytics event | batch เขียนวันละครั้งด้วย Cron Trigger (Workers Free มี 5 triggers[2]) | INSERT ต่อ event |

**บันทึก:** `apps/api/app/core/database.py` ไม่ได้ตั้ง pool tuning ใด ๆ (`create_engine` เรียกเปล่า ๆ) → ตอนย้ายไป Neon ต้องใช้ **pooled endpoint (PgBouncer transaction mode)** ไม่ใช่ direct connection และตั้ง `pool_size`, `pool_pre_ping=True`, `pool_recycle` ด้วย

#### ข้อ 2.4.4 ทางออกเมื่อชน limit

| ทางออก | ต้นทุน | ผล |
|---|---|---|
| **A. Batching + pooled endpoint + ย้าย content ไป R2** | ฿0 | **+28.6 เท่า headroom → ~350–429 คน** |
| B. Neon Launch (overage) | $0.106/CU-hr, ไม่มีขั้นต่ำ[4][6] | 5,000 คน = $140.89/mo = **฿4,931/เดือน (฿0.99/คน)** |
| C. Workers Paid | $5/เดือน (10M req รวม)[1] | เริ่มมีผลที่ ~7,600 คน |
| D. Shard Neon เป็น 2–4 โปรเจกต์ | ฿0 | ×2 หรือ ×4 CU budget |

> **สรุป: ไม่ต้องเลือกระหว่าง "Free" กับ "Paid" ตอนนี้ — ให้ออกแบบให้ถูกตั้งแต่แรก แล้วค่อยอัปเกรด Neon Launch เมื่อถึงจุด** เพราะขั้นต่ำของ Neon Launch = 0 บาท

### 5.3 Retention Model — จุดที่ทำให้เด็กใช้ต่อเนื่อง

#### โมเดล: "สัปดาห์ที่มีเป้าหมาย" (Weekly Goal Loop)

```
วันจันทร์  → ระบบเลือกโจทย์ประจำสัปดาห์ให้อัตโนมัติ
              (อิงจาก skill_mastery ที่มีอยู่แล้ว 28 แถว)
วันธรรมดา → เด็กทำ 1 เควส (3–5 ข้อ) = 5–8 นาที
              ได้ XP → เห็น progress bar ขยับ
วันศุกร์  → สรุปสัปดาห์: "คุณทำถูก X%, จุดอ่อนคือ Y"
              → ส่งรายงานให้พ่อ/แม่ (นี่คือ activation ของผู้ปกครอง!)
สัปดาห์ถัดไป → ตั้งเป้าหมายใหม่ที่ท้าทายขึ้นเล็กน้อย
```

**ทำไมต้องเป็นรายสัปดาห์:** `streak_count` ต้องเป็นรายวันเพื่อสร้าง habit แต่ **โควตาต้องรายสัปดาห์** เพื่อไม่ให้เด็กหมดสิทธิ์ในวันแรก — สองอย่างนี้ทำงานร่วมกันได้ (streak รายวัน, โควตารายสัปดาห์)

## 8) ข้อเสนอ 3 ข้อแรกสำหรับพี่แอร์

1. **อย่าเพิ่งรื้อเนื้อหาจนกว่าจะแก้ 3 อย่างนี้เสร็จ**: Stripe production ที่ชำระเงินได้จริง, `free_test_limit` เป็นรายสัปดาห์, และมี `lesson_activity.completed` — เพราะทั้งสามอย่างนี้คือ**เครื่องวัด** ถ้าไม่มีเครื่องวัด การรื้อเนื้อหา 150 ชั่วโมงจะกลายเป็นการเผาเงินแบบมองไม่เห็นผล

2. **ราคา ฿199/เดือน + PromptPay** เป็นการทดลองที่ถูกที่สุดที่ได้ข้อมูลมากที่สุด — margin ยัง >90% ทั้งที่ลดราคา 33% และเลือกช่องทางจ่ายที่ถูกที่สุด

3. **Neon จะพังที่ ~350 คน ไม่ใช่ Workers** — แก้ batching ก่อน (ฟรี, ได้ +28.6 เท่า headroom) แล้วค่อยตัดสินใจอัปเกรด Neon Launch (ไม่มีค่าขั้นต่ำ) เมื่อถึงจุด
